# Compiler option research

Checked on 2026-11-11. The v1 decision is server-side TeX Live with a fixed offline runtime, invoked through a separate sandbox. The operating-system boundary is mandatory regardless of engine choice.

| Option     | Benefits                                                                                                                                                                                      | Costs and constraints                                                                                                                                                                                                                 |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TeX Live   | Standard package ecosystem and separate pdfLaTeX/XeLaTeX profiles suit the requested template families. A fixed installation makes browser clients small and compilation behavior consistent. | Larger installation and package maintenance. A distribution is not a sandbox. Installation must finish before user compilation; source cannot trigger package downloads or select executables.                                        |
| Tectonic   | Compact XeTeX-based workflow with automatic compilation passes and cached support files. Its CLI provides untrusted mode and cached-only resource resolution.                                 | Those flags do not replace filesystem/process isolation. An offline deployment must provision the full required bundle first. Compatibility still needs testing for each supported template and its fonts.                            |
| SwiftLaTeX | Browser WebAssembly engines keep compilation local to the user's device. Its project includes pdfTeX/XeTeX-related engines and an on-demand package approach.                                 | Package/font delivery, client memory, cancellation, cache behavior, and template fidelity become browser responsibilities. A separate authoritative server pipeline would duplicate compatibility work.                               |
| busytex    | WebAssembly packaging of TeX Live programs can reuse familiar engines. Browser workers can isolate synchronous compile work from the UI.                                                      | Runtime and package data need delivery and versioning. Device-dependent startup/resource behavior and browser integration need their own verification. It remains a future local-compilation option rather than a second v1 compiler. |

The choice favors compatibility and a single tested compilation path. The sandbox receives only a packaged read-only runtime and job inputs, with no application credentials or network access. Fixed arguments disable shell escape, including write18 execution. Resource controls must cover wall time, CPU, memory, files, writable scratch, and output collection. A compiler failure must preserve the last successful PDF with a visible stale indicator.

Sources: [TeX Live guide](https://tug.org/texlive/doc/texlive-en/texlive-en.pdf), [Kpathsea security](https://texdoc.org/serve/kpathsea/0), [Tectonic compile security](https://tectonic-typesetting.github.io/book/latest/v2cli/compile.html), [Tectonic cached-only builds](https://tectonic-typesetting.github.io/book/latest/v2cli/build.html), [SwiftLaTeX source and documentation](https://github.com/SwiftLaTeX/SwiftLaTeX), [busytex source and documentation](https://github.com/busytex/busytex), and [TinyTeX release distribution](https://github.com/rstudio/tinytex-releases).

The final runtime policy and measured template/test outcomes belong in `docs/compilation.md`; this comparison does not claim that an untested engine or isolation configuration works.
